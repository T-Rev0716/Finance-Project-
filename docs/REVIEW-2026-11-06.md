## Judgment

A useful portfolio-review prototype with a coherent advisor workflow: upload → deterministic findings → saved analysis → client meeting brief. Keep Next.js/FastAPI and finish this workflow before expanding into a full financial planning suite. Deterministic evidence, input hashes, versioned results, and fallback briefs are credible interview topics.

This is currently a synthetic-data demo. It is not ready to hold real client records. The API has no authentication or per-user ownership checks, including history, individual analyses, reports, and generation endpoints. CORS does not provide authorization.

## Implemented in this branch

- Consolidate security exposure by normalized ticker across account rows, regardless of display-name variants. Apply the same identity to top holdings and concentration rules; preserve original rows for account-specific tax observations.
- Reject conflicting asset-class/sector labels for a ticker and consolidate equivalent sector capitalization.
- Reject infinite numbers, missing required text, overflowed totals and unrepresentable portfolio gain/loss percentages before analysis/persistence.
- Bound the upload endpoint's read to the configured limit plus one byte. This does not replace infrastructure-level request limits or rate limiting.
- Increment engine version to 0.1.1 so new results are distinguishable from historical analyses. Historical results remain unchanged.
- Add 20 regression cases covering validation, exposure consolidation, API rejection, and upload read bounds.

## Priorities before real client use

1. **Identity and access:** advisor sign-in, household ownership, authorization on every analysis/brief/export path, cross-user denial tests, server-side request limits, separate synthetic demo mode. Verify backup and restore before promising persistence.
2. **Financial data contract:** security identifiers beyond ticker when multiple exchanges/currencies are supported; account IDs; valuation date; currency; supported asset classifications; explicit handling of conflicting household profiles. Currently mixed risk profiles use the first row with a warning. Unknown asset-class labels can still miss equity rules.
3. **Model limitations:** sector labels supplied for funds are not look-through sector exposure. Cash above 10% may be intentional; add liquidity needs, time horizon, and policy targets. Fixed thresholds are illustrative review rules, not personalized investment policy.
4. **LLM reliability:** fact-token checks restrict vocabulary/numbers but do not prove relationships. A narrative can assign an existing number to the wrong holding. Add adversarial relational-grounding examples; require advisor review of generated prose. A banned-phrase list does not establish regulatory compliance.
5. **Reproducibility:** locked Python dependency versions and automated backend/frontend checks including a provisioned Chromium browser. Compare stored report outputs after engine changes. The checked-in sample report should be regenerated under 0.1.1 when browser rendering is available; this branch does not claim that happened.

## Product roadmap

### Next feature: advisor review workflow

Add a household/valuation header, explicit policy assumptions, stable finding IDs, and a review queue with Open / Discussed / Follow-up / Resolved states, advisor notes, and an append-only event history. Tie decisions to a particular analysis version, then carry selected follow-ups into the meeting brief. A note saved against one household must never appear in another household. This makes the existing findings useful throughout a meeting and its follow-up.

### Then: usability and visual refinement

The source shows a consistent, restrained Tailwind interface. A rendered visual assessment was blocked, so no visual quality score is assigned. Prioritize the actual workspace: clear household identity, readable allocation comparisons, prominent next actions, a structured evidence drawer, keyboard-accessible upload controls, loading/error/empty states, and mobile table containment. The existing top-holdings table lacks a local horizontal-scroll wrapper and needs a browser check at narrow widths. Verify desktop and mobile screenshots before accepting a redesign.

### Then: target allocation and scenarios

Add advisor-selected target allocations, drift in percentage points, contribution-first hypothetical adjustments, and saved baseline/alternative comparisons. Require cash-flow and tax-context limitations to be visible. Follow with a separately tested retirement module only after the portfolio-review workflow is dependable.

## Resume positioning

Describe the implemented project as a portfolio-review and meeting-preparation application. Explain cross-account exposure aggregation, evidence-backed rules, auditability, and testing. Do not claim automated compliance, live brokerage integrations, comprehensive financial planning, real-client deployment, or LLM factual guarantees.
